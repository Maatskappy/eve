title: "Sandbox"
description: "Configure the isolated filesystem and command environment used by an eve agent."
---

Every eve agent has one sandbox with a workspace root: `/workspace` in Vercel and Docker sandboxes, or a real directory on your machine with the [host sandbox](/docs/sandbox/host). The built-in `bash`, `read_file`, and `write_file` tools use it. Without an authored sandbox file, eve selects the best available environment automatically.

## Use the sandbox

Authored tools and callbacks access the live sandbox with `ctx.getSandbox()`:

```ts title="agent/tools/run_analysis.ts"
import { defineTool } from "eve/tools";
import { z } from "zod";

export default defineTool({
  description: "Run a Python script.",
  inputSchema: z.object({ script: z.string() }),
  async execute({ script }, ctx) {
    const sandbox = await ctx.getSandbox();
    await sandbox.writeTextFile({ path: "analysis.py", content: script });
    const result = await sandbox.run({ command: "python analysis.py" });
    if (result.exitCode !== 0) throw new Error(result.stderr);
    return result.stdout;
  },
});
```

Relative paths resolve under the workspace root, which is also where commands start. `run()` returns `{ exitCode, stdout, stderr }`; a nonzero exit code does not throw automatically. Use `spawn()` for a long-running process.

Built-in environments set `AI_AGENT=eve` on every `run()` and `spawn()` call, including the `bash` tool and `prepare`, so agent-aware CLIs such as `vercel` skip interactive prompts. To use a different value, set `AI_AGENT` in the environment's `env` option or pass it in the `env` of one `run()` or `spawn()` call.

Pass the configured environment to preserve its specific session capabilities in authored runtime code:

```ts
import { environment } from "../sandbox";

const sandbox = await ctx.getSandbox(environment);
await sandbox.setNetworkPolicy("deny-all");
```

For example, a Vercel environment returns a handle with `setNetworkPolicy()`. The common handle from `ctx.getSandbox()` does not expose provider-specific capabilities. The environment must match the one configured for the current sandbox.

## Define an environment

A sandbox module exports an environment and returns a sandbox from `defineSandbox()`:

```ts title="agent/sandbox.ts"
import { DefaultSandbox, defineSandbox } from "eve/sandbox";

export const environment = DefaultSandbox.environment();
export default defineSandbox(() => environment.open());
```

`environment.open()` starts the persistent sandbox owned by the current eve session. The `defineSandbox()` selector runs until initialization succeeds, then eve checkpoints the selected provider and its state. Later workflow steps and process restarts call the provider's `resume()` directly without rerunning the selector or `environment.open()`.

Pass options for the live sandbox to `open()`, then configure the returned sandbox before returning it. `open()` applies its options only when it creates the sandbox. Initialization can run more than once against the same sandbox, for example when a subagent that shares the sandbox opens it before the parent does, when a [workflow step](/docs/tools/workflows#use-the-session-sandbox-in-a-step) opens it before the session records it, or on the next access after an initialization that failed. Make it safe to repeat:

```ts
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";

export const environment = VercelSandbox.environment();

export default defineSandbox(async ({ session }) => {
  const sandbox = await environment.open({ networkPolicy: "deny-all" });
  await sandbox.writeTextFile({ path: ".eve/session", content: session.id });
  return sandbox;
});
```

The environment export is required because `eve build` prepares immutable environment inputs before a session exists.

### Prepare a reusable environment

Use the environment's `prepare` option for setup every new sandbox inherits:

```ts
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";

export const environment = VercelSandbox.environment({
  prepare: async (sandbox) => {
    const result = await sandbox.run({
      command: "sudo apt-get update && sudo apt-get install -y jq",
    });
    if (result.exitCode !== 0) throw new Error(result.stderr);
  },
});

export default defineSandbox(() => environment.open());
```

eve runs `prepare` while creating a reusable provider artifact, not once for each live session sandbox. Vercel captures a snapshot; Docker captures an image; and the host sandbox captures a template directory that each session copies.

During `eve dev`, startup and authored-source rebuilds do not prepare sandbox environments. The first sandbox access prepares all environments in that compiled generation before opening the requested sandbox. This includes environments declared by subagents and extensions, even if they use different providers. Concurrent requests share the preparation work; a failed preparation can be retried on a later access. Optional provider installation and setup can make that first access slow.

`eve build` still prepares environments eagerly. In production, eve passes the recorded artifact directly to the provider when it creates a live sandbox. Production runtime does not rebuild or repair a missing artifact. A missing image, snapshot, or template fails with rebuild or redeploy guidance.

### Reuse native resources across sessions

Built-in environments do not expose cross-session sharing. To reuse native compute or storage across eve sessions, define a custom provider that returns a session-owned logical sandbox view and keeps shared resources outside that view's `stop`, `shutdown`, and `delete` operations. A session-specific path is not an isolation boundary; mutually untrusted sessions require separate native compute or stronger provider-owned isolation.

### Share a parent sandbox

A declared subagent can use its dispatching parent's sandbox explicitly:

```ts title="agent/subagents/reviewer/sandbox.ts"
import { defineParentSandbox } from "eve/sandbox";

export default defineParentSandbox();
```

An inheriting subagent cannot declare its own managed workspace or skill files.

The parent and every subagent that shares its sandbox, including children of the built-in `agent` tool, use one sandbox keyed by the parent's session. Whichever session opens it first runs the parent's `defineSandbox()` selector to create it. When the parent session ends, eve deletes the sandbox, even one that only a subagent opened.

## Managed workspace and skills

Use the sandbox directory for authored workspace seeds:

```text
agent/sandbox/
  sandbox.ts
  workspace/
    schema.sql
```

Files under `agent/sandbox/workspace/` seed the writable workspace root. eve copies the seed when it prepares a new environment generation. Existing live sandbox state is not overwritten by later seed changes.

Agent skills are compiled into a separate resource tree and exposed at `$HOME/.agents/skills`. Instructions and tools can refer to `$HOME/.agents/skills` with every built-in provider; file tools resolve it to the provider's skill directory. Refer to workspace files with relative paths, or with `/workspace` only when you pin a Vercel or Docker sandbox. Do not refer to a concrete home directory or `/eve/resources`, which is provider-internal staging.

Providers receive both trees with explicit metadata:

```ts
interface SandboxProviderResources {
  source:
    | { kind: "none" }
    | { kind: "inline"; key: string }
    | { kind: "materialized"; key: string; path: string }
    | { kind: "reference"; key: string };
  workspace?: SandboxProviderResourceTree;
  skills?: SandboxProviderResourceTree;
}

interface SandboxProviderResourceTree {
  key: string;
  files: ResourceFile[];
  mountPath: string;
  targetPath: string;
}
```

Docker mounts the compiled trees read-only under `/eve/resources`, copies workspace seeds into writable `/workspace`, and exposes skills read-only where possible. Vercel's snapshot environment writes workspace and skill contents before capturing its snapshot. Custom providers decide whether to upload, mount, or write each tree, but must expose the final target paths before authored preparation runs.

## Inbound attachments

eve writes byte-backed files that reach the agent into the sandbox under `.eve/attachments/` in the workspace root (`/workspace/.eve/attachments/` in Vercel and Docker sandboxes) and keeps only a reference in session history. This covers files attached to user messages and files that tools return to the model with `toolOutputPart.file` or as MCP image, audio, and blob content.

Before every model call, eve reads the referenced files back from the sandbox. Every file, whether attached to a message or returned by a tool, reaches the model with a label that names its sandbox path, such as `Attached file /workspace/.eve/attachments/<hash>/report.csv (text/csv)`. The agent can open that path with `read_file` or `bash`. The file's bytes follow its label only when every major provider reads the format natively:

- A PNG, JPEG, GIF, or WebP image up to 3 MiB and at most 8000 pixels per side.
- A PDF up to 20 MiB.

Other files, such as CSV, HEIC, audio, and video, reach the model as the label alone. eve checks image and PDF media types against the file's bytes when it stages the file. A file whose bytes don't match its declared image or PDF type is staged as `application/octet-stream`, so a provider never receives bytes it would reject.

To let the agent answer voice notes and other audio, add a tool that transcribes the staged file. See [Voice notes](/docs/patterns/voice-notes).

If a referenced file is missing, or its bytes no longer match what eve staged because something in the sandbox overwrote it, the model receives a `FileNotFound` note in its place.

A file that eve can't stage never enters session history. When a channel's `fetchFile` fails, or a file part's `data` is not bytes, base64, a `data:` URL, or a URL, the model receives a note that names the file instead.

Each call sends the same bytes for the same file, so the model still sees attachments from earlier turns and the provider's prompt cache stays valid. Compaction replaces files in older tool results with their text reference. The `read_file` tool shows the same images and PDFs to the model as files, so the agent can look at an attachment again after compaction, or open a PDF that a tool or `bash` wrote to the sandbox.

## Custom providers

eve offers two ways to add a sandbox engine:

- **Sandbox backends:** define one with `defineSandboxBackend()` for an engine that runs on the machine running eve, such as a local VM, container, or shell runtime. You describe how to open, find, and remove a sandbox for a session; eve provides sessions, seeding, preparation, and cleanup. Backends keep each build's files under the app's `.eve/sandbox-cache/<name>/` directory, so build and run the app on the same machine.
- **Full-control providers:** define one with `defineSandboxProvider()` for anything else, such as remote sandboxes, snapshots, network policies, or state that must survive a move to another machine.

### Sandbox backends

A backend opens its engine's sandbox for a session and returns an instance that runs commands and reads and writes files. This example wraps Acme VM, a hypothetical engine that runs microVMs on the same machine:

```ts
import { defineSandboxBackend, type SandboxBackendInstance } from "eve/sandbox/provider";
import { AcmeVm, type AcmeVmHandle } from "acme-vm";

function adapt(vm: AcmeVmHandle): SandboxBackendInstance {
  return {
    exec: ({ command, cwd, env }) => vm.run(command, { cwd, env }),
    readFile: (path) => vm.readFileOrNull(path),
    writeFile: (path, content) => vm.writeFile(path, content),
    stop: () => vm.stop(),
  };
}

export const AcmeVmSandbox = defineSandboxBackend<{ image?: string }>({
  name: "acme-vm",
  workspaceRoot: "/workspace",
  async open(ctx, options) {
    // Returns the VM with this name, or atomically creates it.
    const { created, vm } = await AcmeVm.findOrCreate({
      image: options.image ?? "ubuntu:24.04",
      name: ctx.key,
    });
    return { created, instance: adapt(vm) };
  },
  async find(ctx) {
    const vm = await AcmeVm.find(ctx.key);
    return vm === undefined ? undefined : adapt(vm);
  },
  remove: (ctx) => AcmeVm.removeIfExists(ctx.key),
});
```

The definition describes the engine:

- `name` names the provider and its cache directory, using lowercase letters, digits, and hyphens. `host`, `docker`, and `vercel` belong to built-in providers.
- `workspaceRoot` is the absolute path where commands start and relative paths resolve. eve writes the agent's workspace files under it.
- `open(ctx, options)` finds or creates the session's sandbox. Concurrent calls for one session, even from separate processes, must end up with the same sandbox. Return `created: true` when this call created it.
- `find(ctx, options)` finds the existing sandbox when eve resumes a session. Return `undefined` when it no longer exists: eve calls `remove()` to clear what is left, then starts the session over with a fresh sandbox. `find()` is required unless the backend sets `directoryTemplate`.
- `remove(ctx, options)` removes the session's sandbox and must succeed when nothing exists. Without it, eve deletes `ctx.directory`.
- `directoryTemplate: true` prepares a template directory once per build and copies it into each new session's `ctx.directory` before `open()`. Use it for engines whose whole state lives in that directory. Without `find()`, eve reopens the session with `open()` while `ctx.directory` exists. eve rebuilds the template when the workspace files, the skills, or `agent/sandbox/sandbox.ts` change. Editing a file that `sandbox.ts` imports does not rebuild it, so delete `.eve/sandbox-cache/<name>/templates/` after such a change.

Every hook receives `ctx` with the session's `key`, a stable name made of lowercase letters, digits, and hyphens that is unique per app directory and session, so it can name a container or VM. `ctx.directory` is the session's directory under the app's `.eve/sandbox-cache/<name>/sessions/`, and `ctx.session` is the session. Because the key includes the app's absolute path, moving the app directory makes eve treat existing sandboxes as gone and create new ones; remove the old ones with your engine's tools.

The instance's `exec()` returns `{ stdout, stderr, exitCode }` once the command finishes, or `{ stdout, stderr, exited, kill }` to stream output; eve calls `kill()` when the command's signal aborts. Output can be strings or bytes. `readFile()` returns `null` when the file does not exist, and `writeFile()` creates parent directories. `removePath()` defaults to running `rm` through `exec()`. eve calls `stop()` for `sandbox.stop()`, `sandbox.delete()`, and server shutdown.

eve provides the rest of the provider contract:

- **Seeding:** when `open()` reports a created sandbox, eve writes the workspace files and skill packages through `writeFile()`, then runs the environment's `prepare` option, which every backend accepts. If any of that fails, eve stops and removes the sandbox so a later open creates it again. With `directoryTemplate`, eve does this once in the template instead.
- **Concurrent opens:** eve seeds after `open()` returns, so another eve process that opens the same sandbox in the meantime can use it before seeding finishes. If several eve processes share one engine, hold a lock, such as a file lock, around `open()` and the first use of the sandbox.
- **Rebuilds:** an existing sandbox keeps its files, and eve replaces its authored skills with the current build's on the next open.
- **Commands:** every command gets `AI_AGENT=eve` plus the `env` eve passes for it. On every open, eve runs one command that reads `$HOME` to find the skill directory.
- **Lifecycle:** eve stops the sandbox for `sandbox.stop()` and server shutdown, stops and removes it for `sandbox.delete()`, and removes it at session end.

### Full-control providers

`defineSandboxProvider()` from `eve/sandbox/provider` exposes the whole provider contract: you prepare a JSON-serializable artifact, start and resume sandboxes, and clean up at session end. The handle's `sandbox` must implement the full `SandboxSession` surface; eve does not build it for you. This example assumes Acme's SDK returns sandboxes that already implement it:

```ts
import type { SandboxSession } from "eve/sandbox";
import {
  defineSandboxProvider,
  type SandboxProviderHandle,
  SandboxSessionGoneError,
} from "eve/sandbox/provider";
import { acme, type AcmeRemoteSandbox } from "acme-sdk";

const createHandle = (sandbox: AcmeRemoteSandbox): SandboxProviderHandle => ({
  sandbox,
  onRuntimeShutdown: async () => {},
  onSandboxDelete: () => sandbox.destroy(),
  onSandboxStop: () => sandbox.stop(),
});
// The session id alone names the sandbox, so every caller finds the same one.
const sandboxName = (sessionId: string) => `eve-${sessionId}`;

export const AcmeSandbox = defineSandboxProvider<
  { image: string; prepare?: (sandbox: SandboxSession) => Promise<void> },
  { networkPolicy?: "allow-all" | "deny-all" },
  { snapshotId: string },
  { name: string; version: 1 }
>({
  name: "acme",
  environment(options) {
    return {
      async prepare(ctx) {
        const files = (ctx.resources.workspace?.files ?? []).map((file) => ({
          content: file.content,
          path: `/workspace/${file.relativePath}`,
        }));
        const snapshot = await acme.snapshot({
          files,
          image: options.image,
          setup: options.prepare,
        });
        return { snapshotId: snapshot.id };
      },
      async start(ctx, liveOptions, artifact) {
        const name = sandboxName(ctx.session.id);
        // Returns the sandbox with this name, or atomically creates it from the snapshot.
        const sandbox = await acme.getOrCreate({
          name,
          networkPolicy: liveOptions?.networkPolicy,
          snapshotId: artifact.snapshotId,
        });
        return { handle: createHandle(sandbox), state: { name, version: 1 } };
      },
      async resume(_ctx, _artifact, state) {
        const sandbox = await acme.find(state.name);
        if (sandbox === undefined) {
          throw new SandboxSessionGoneError(`Acme sandbox "${state.name}" no longer exists.`);
        }
        return createHandle(sandbox);
      },
      async onSessionEnd(ctx, state) {
        // `state` is null when the session never recorded it, for example when
        // only a subagent that shares the sandbox opened it.
        await acme.deleteIfExists(state?.name ?? sandboxName(ctx.session.id));
      },
    };
  },
});
```

The generic parameters describe environment options, live options, the prepared artifact, minimal serialized session state, and an optional provider-specific sandbox session type. `prepare()` returns the complete JSON-serializable artifact.

`start()` must be an idempotent upsert keyed by `ctx.session.id`: return the live sandbox for that key when one exists, and create it otherwise. eve can call `start()` for one key more than once, from different processes and deployments, and concurrently. A subagent that shares its parent's sandbox can open it before the parent does, and two processes can race to create it. Derive the sandbox's identity from the key, plus a provider-level namespace such as a project or account when names would otherwise collide. Never derive it from the open options or the artifact, which can differ between callers and deployments; apply them only when `start()` creates the sandbox. eve persists the minimal JSON-compatible state `start()` returns. Process restarts call `resume()` with only the current context, that state, and the target deployment's exact artifact.

`onSessionEnd()` is required. eve calls it for every owning durable session that reaches a completed, expired, or failed terminal outcome, including sessions with no recorded sandbox state. A failed step or process loss can create a sandbox before its state is checkpointed, so the last checkpoint cannot establish that no sandbox exists. The hook receives the session context, the persisted provider state or `null`, and a `reason` of `"completed"`, `"expired"`, or `"failed"`. Delete whatever exists under `ctx.session.id` without depending on a live handle, and find it from the key when the state is `null`. The hook must succeed when nothing exists and must be idempotent: eve retries the cleanup step and logs an exhausted failure without replacing the session's terminal outcome. A subagent that shares its parent's sandbox does not call the hook, because cleanup belongs to the parent. An `invokeTool` call without a key also calls `onSessionEnd()` when the call ends if it requested sandbox access, including an initialization attempt that failed.

Provider handles implement `onSandboxStop()`, `onRuntimeShutdown()`, and `onSandboxDelete()`. These handle-level methods cover authored stop or delete calls and process shutdown; `onSessionEnd()` is the single provider hook for durable terminal session cleanup. When the initialization that `defineSandbox()` runs after `open()` fails, eve does not delete the sandbox: the next access runs the selector against it again, and session end removes it.

Open options belong to `start()` and are not serialized or passed to `resume()`. A provider must put any immutable option-derived data needed for reconnection in its session state. With the current immutable-state contract, `resume()` reconnects existing native state and does not recreate it, because initialization that `defineSandbox()` runs after `open()` would not run again.

When the native sandbox no longer exists, throw `SandboxSessionGoneError` from `resume()`, as the example does. eve then clears the session's provider state and reruns the selector, whose `start()` creates a fresh sandbox, as after `sandbox.delete()`. Any other error from `resume()` leaves the state in place, so every sandbox call in that session fails with that error until the session ends.

Preparation discovers authored files through `ctx.files`; core keeps project layout and artifact storage keys private. Keep provider SDK values behind the provider. `environment.open()` preserves the provider's sandbox capability type, while the heterogeneous runtime registry erases it to eve's common session surface.

The handle's `sandbox.resolvePath()` declares the sandbox's workspace root: relative paths resolve from it, and `resolvePath(".")` is the directory that `glob`, `grep`, attachment staging, and error messages use. `readFile()` returns `null` when the file does not exist.

### Skill directory

eve writes skill packages to `$HOME/.agents/skills`, using the sandbox's own `$HOME`. To keep skills somewhere else, set `EVE_SANDBOX_SKILL_ROOT` to an absolute directory in the environment of every command your provider or backend runs. eve reads it once per session and writes skills there instead.

### Example providers

eve no longer ships providers for just-bash or microsandbox. These guides define each as a sandbox backend:

- [just-bash](/docs/sandbox/just-bash): a TypeScript bash interpreter over a per-session directory on local disk, with custom commands and mounts.
- [microsandbox](/docs/sandbox/microsandbox): one local microVM per session from any OCI image.

## Lifecycle

Session-owned sandboxes persist across turns and deployments while their provider state remains available. `sandbox.stop()` stops compute without deleting persisted state; a later access resumes that state directly. `sandbox.delete()` deletes the sandbox and clears provider state, so the next `ctx.getSandbox()` reruns the selector, and the provider starts a fresh sandbox under the same session key from the current environment. If the native sandbox is gone when a session resumes, for example after a local daemon restart, a removed container, or a deleted host sandbox session directory, eve does the same: the session continues in a fresh sandbox, without the lost sandbox's files. When the durable session reaches a terminal outcome, eve calls the provider's `onSessionEnd()` hook to delete what remains under the session's key.

Before that cleanup, session end ends the session's task runs, and each run resets the subagent sessions it opened. eve does not wait for those subagents to stop. A subagent step that is still running at that moment can open the sandbox again after cleanup, and eve does not remove a sandbox created that late.

Changing sandbox source, preparation code, Dockerfile content, environment options, workspace resources, or skills produces a new environment generation. Existing durable sessions keep their sandbox, because its identity comes from the session key alone; new sessions use the current generation.
